# Writing Human-Readable Automation

Writing code that works is great, but if you're the only one who can read it... you've got a problem. In this video, we cover 5 ways you can start to refactor your network automation to make it easier for your fellow network engineer or developer to read. We use our "last time int state up" script as the example.

## Dive deeper into the material
The following prompt guide is meant to help you further explore the lesson. Please keep in mind that results will vary each time the prompt is submitted, even if the same model is used. Results will also vary between models. For this reason, we cannot guarantee response outputs.

Ask as many questions as needed when getting a response to help you clarify. Rabbit holes are encouraged! And practicing the concepts you're learning is a must for retention and comprehension :D

1. What is refactoring?
2. Why do we refactor our code?
3. Give me the 5 simplest ways to refactor code, and provide examples of them related to network automation.
^^^ (dive deeper into this depending on what it responds with!)
4. What is the Python convention for naming variables and functions?
5. How often should we factor our code? Are there times I shouldn't refactor a script? Give me realistic network ops scenarios where leaving the code alone might be best.
6. Give me a comprehensive list of tasks that are considered refactoring. 
7. What security problems can show up during refactoring?
8. Here is a script I'd like to refactor. First, explain the single responsibility principle to me and let me know if this script follows that. Next, tell me how I could better name my functions and variables. Finally, if you could give me one final refactoring suggestion, what would it be and why?
9. What's a "magic string"? Give me an example. Tell me why they show up in network automation and what to do about them.
10. Quiz me with 5 short before-and-after code snippets. For each one, I'll say whether it's a good refactor, a bad one, or beyond refactoring (i.e. changes the script's behavior).
11. "I just refactored this script: [paste before and after]. Help me evaluate how well I refactored it. Did the script's behavior stay the same? What refactoring opportunities did I miss?
